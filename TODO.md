# Проект: Microbots Arena

## Текущий статус реализации

Этапы 1–8 выполнены, включая задачи UI-полировки из прежней передачи Astra Low. Проверены серверная логика, ограничения DSL, комнаты и права хоста; в рамках MVP незакрытых задач, требующих Astra Medium, не выявлено. Отдельный список Medium не создан, поскольку подтверждённых задач для него нет.

Результаты ревью, проверки и принятые ограничения: [HANDOFF.md](HANDOFF.md). Запуск и инструкция игрока: [README.md](README.md). Ниже сохранено исходное техническое задание; перечни этапов описывают требования, а не незавершённую работу.

Нужно разработать браузерную многопользовательскую игру для обучения программированию.

Игроки подключаются к одной игровой комнате через браузер. Каждый игрок получает базу и стартового микробота. Микроботы управляются программами, написанными учениками.

Цель игрока — собирать ресурсы, создавать новых микроботов, программировать их поведение и уничтожить остальных игроков.

Побеждает последний оставшийся игрок.

---

# 1. Общий принцип разработки

Главный приоритет:

**сначала рабочая игровая симуляция, затем multiplayer, затем программирование ботов, затем UI и улучшения.**

Не переусложнять архитектуру.

Следовать принципам:

- KISS;
- минимальное количество зависимостей;
- не создавать абстракции без необходимости;
- не создавать универсальные системы "на будущее";
- не использовать микросервисы;
- не использовать БД в MVP;
- не использовать Docker, если он не нужен для запуска проекта;
- не использовать Unity;
- не использовать React/Vue без объективной необходимости;
- не добавлять функции, которых нет в ТЗ.

Если задача решается простой функцией или классом — использовать простую функцию или класс.

Каждый этап должен оставлять проект в запускаемом состоянии.

# 4. Архитектурный принцип

Сервер является единственным авторитетным источником состояния игры.

Клиент:

- принимает состояние;
- отображает игру;
- отправляет команды;
- отправляет код игрока.

Клиент НЕ должен определять:

- урон;
- HP;
- количество ресурсов;
- возможность создания бота;
- положение сущностей;
- победителя;
- факт попадания;
- результаты выполнения программы.

Вся игровая логика выполняется на сервере.

# 5. Game Loop

Создать серверную игровую симуляцию.

Использовать фиксированный tick.

Ориентировочно:

```text
10 ticks/sec
```

То есть:

```js
100 ms / tick
```

Game должен иметь примерно следующую структуру:

```js
class Game {
    players = [];
    bots = [];
    bases = [];
    resources = [];

    tick() {}
}
```

Не привязывать игровую механику напрямую к Socket.IO.

Game должен уметь работать независимо от сетевого слоя.

---

# 6. Карта

Для MVP использовать простую прямоугольную карту.

Например:

```text
1600 × 900
```

Размер вынести в конфигурацию.

Препятствий пока нет.

Карта представляет собой свободное пространство.

---

# 7. Player

Игрок должен содержать минимум:

```js
{
    id,
    name,
    resources,
    alive,
    color
}
```

У игрока есть:

- одна база;
- принадлежащие ему микроботы;
- общий запас ресурсов.

---

# 8. Base

База содержит:

```js
{
    id,
    ownerId,
    x,
    y,
    hp,
    maxHp
}
```

Ориентировочно:

```text
HP = 1000
```

Уничтожение базы должно иметь значение для поражения игрока.

---

# 9. Bot

Микробот содержит:

```js
{
    id,
    ownerId,

    x,
    y,

    hp,
    maxHp,

    speed,

    attackDamage,
    attackRange,
    attackCooldown,

    visionRange,

    target,

    program
}
```

Можно добавить минимально необходимые runtime-поля.

Не хранить состояние, которое легко вычисляется из других данных, если это не нужно.

---

# 10. Resource

Ресурс:

```js
{
    id,
    x,
    y,
    amount
}
```

Ресурсы случайно распределяются по карте.

После истощения ресурс исчезает.

Сервер периодически создаёт новые ресурсы.

Параметры должны находиться в конфигурации.

Например:

```text
initialResources = 40
resourceAmount = 20
resourceRespawnInterval = 5000 ms
```

---

# 11. Движение

Бот должен уметь получать цель:

```js
moveTo(x, y)
```

`moveTo()` не должен мгновенно менять координаты.

Он только задаёт направление/цель движения.

На каждом tick Game перемещает бота в сторону цели с учётом скорости.

Когда бот достигает цели, он останавливается.

---

# 12. Сбор ресурсов

Бот должен уметь:

```text
collect()
```

Ресурс можно собирать только рядом с ботом.

Например:

```text
collectRange = 25
```

Собранный ресурс добавляется общему запасу владельца бота.

Не делать отдельный инвентарь каждому микроботу в MVP.

---

# 13. Создание новых ботов

Новый бот создаётся возле базы.

Стоимость:

```text
30 ресурсов
```

Значение вынести в конфигурацию.

API:

```text
spawn()
```

Условия:

- база игрока существует;
- ресурсов достаточно.

После вызова:

```text
player.resources -= botCost
```

Создать нового бота возле базы.

---

# 14. Поиск объектов

Бот не должен иметь доступ ко всей карте.

Он видит только объекты внутри `visionRange`.

Ориентировочно:

```text
visionRange = 250
```

Реализовать API:

```text
nearestEnemy()
nearestResource()
nearestFriendly()
```

Функции должны учитывать радиус зрения.

Можно также реализовать:

```text
scan()
```

если это упрощает API.

---

# 15. Бой

Микробот может атаковать:

- вражеского микробота;
- вражескую базу.

API:

```text
attack(target)
```

Атака возможна только если:

```text
distance <= attackRange
```

Необходимо учитывать cooldown.

Примерные параметры:

```text
Bot HP = 100
Damage = 10
Attack range = 35
Attack cooldown = 500 ms
```

После:

```text
hp <= 0
```

сущность уничтожается.

---

# 16. Поражение и победа

Для MVP игрок проигрывает, если:

```text
его база уничтожена
И
у него не осталось микроботов
```

До тех пор пока хотя бы один бот жив, игрок ещё считается живым.

Когда остаётся один живой игрок:

```text
GAME OVER
```

Определить победителя.

Остановить симуляцию.

---

# 17. Встроенный AI

ДО добавления пользовательского программирования реализовать простой AI.

Он нужен для проверки полной игровой механики.

Пример поведения:

```text
если рядом враг:
    атаковать

иначе если виден ресурс:
    идти к ресурсу
    собирать

иначе:
    двигаться случайно

если ресурсов достаточно:
    создавать нового бота
```

Не переходить к следующей крупной стадии, пока два встроенных AI не способны полностью сыграть матч от начала до определения победителя.

---

# 18. Multiplayer

После полной готовности симуляции подключить Socket.IO.

Нужно реализовать комнаты.

Игровая комната имеет короткий код, например:

```text
ABCD
```

Учитель создаёт комнату.

Ученики вводят:

- имя;
- код комнаты.

Пример:

```text
Имя: Roman
Комната: ABCD
```

После подключения игрок появляется в lobby.

---

# 19. Lobby

Хост должен видеть список игроков.

Пример:

```text
ROOM ABCD

Roman     READY
Alex      READY
Dima      NOT READY

[START]
```

Игрок должен иметь возможность:

```text
READY / NOT READY
```

Хост может начать матч.

После начала матча подключение новых игроков можно запретить.

---

# 20. Расстановка игроков

При запуске матча базы игроков должны быть распределены по карте достаточно далеко друг от друга.

Для MVP можно расположить их:

- по окружности;
- по краям карты;
- по заранее вычисленным позициям.

Не нужно писать сложный алгоритм procedural placement.

---

# 21. Сетевая синхронизация

Сервер должен периодически отправлять игровое состояние клиентам.

Пример:

```js
{
    players: [],
    bots: [],
    bases: [],
    resources: [],
    gameState: "running"
}
```

Можно использовать частоту около:

```text
10 обновлений/sec
```

Клиент только интерпретирует и отрисовывает состояние.

Для MVP interpolation необязателен.

Не выполнять произвольный JavaScript через:


# 25. Язык программирования ботов

Для MVP сделать маленький DSL, синтаксис которого напоминает Python/JavaScript.

Не нужно писать полноценный Python.

Он должен поддерживать минимально:

```text
переменные
if
else
простые выражения
вызовы функций Bot API
```

Например:

```text
enemy = nearestEnemy()
resource = nearestResource()

if enemy:
    attack(enemy)
else:
    if resource:
        moveTo(resource)

if canSpawn():
    spawn()
```

Если полноценные циклы значительно усложняют интерпретатор — в первой версии их не делать.

Программа и так выполняется каждый game tick.

То есть вместо:

```text
while true
```

вся программа автоматически запускается снова на следующем tick.

Это предпочтительная модель.

---

# 26. Bot API

Минимальный API:

```text
nearestEnemy()
nearestResource()
nearestFriendly()

moveTo(target)
moveTo(x, y)

attack(target)

collect()

canSpawn()
spawn()

distance(target)

random()
```

Можно добавить:

```text
getHealth()
getResources()
getPosition()
getBase()
```

только если они нужны для полезных стратегий.

Не добавлять десятки функций.

---

# 27. Ограничение выполнения программ

Каждый бот должен иметь ограниченный бюджет вычислений.

Например:

```text
100 operations / tick
```

Каждая операция имеет стоимость.

Пример:

```text
переменная             1
арифметическая операция 1
moveTo()                1
attack()                2
nearestResource()       5
nearestEnemy()          5
scan()                 10
```

Если лимит исчерпан:

```text
остановить выполнение программы этого бота до следующего tick
```

Это должно предотвращать зависание сервера из-за пользовательского кода.

---

# 28. Ошибки программы

Интерпретатор должен возвращать понятные ошибки.

Например:

```text
Line 4:
Unknown function "attak"

Did you mean "attack"?
```

Ошибки одного игрока не должны останавливать:

- сервер;
- комнату;
- остальных игроков;
- game loop.

Если программа содержит ошибку, бот просто не выполняет действия.

---

# 29. Применение кода

Игрок пишет код и нажимает:

```text
APPLY
```

Сервер:

1. получает текст программы;
2. парсит;
3. проверяет;
4. при успехе сохраняет программу;
5. назначает её ботам игрока.

Новые боты также должны получать текущую программу игрока.

Для MVP достаточно одной программы на всех ботов игрока.

---

# 30. Отладочная информация

Добавить минимальный debugger/log.

Например:

```text
Bot #23

nearestEnemy() -> null
nearestResource() -> resource_8
moveTo(resource_8)

CPU: 89 / 100
```

Не отправлять огромные логи от всех ботов постоянно.

Можно позволить игроку выбрать одного бота для просмотра debug-информации.

Если это сильно затягивает разработку — сделать только список ошибок программы.

---

# 31. Restart

Хост должен иметь кнопку:

```text
RESTART MATCH
```

При restart:

- сохраняются игроки;
- сохраняются их программы;
- удаляются боты;
- базы восстанавливаются;
- ресурсы генерируются заново;
- стартовые боты создаются заново;
- начинается новый матч.

# 35. Порядок работы Codex

Не пытайся реализовать весь проект одним гигантским изменением.

Работай небольшими завершёнными этапами.

Для каждого этапа:

1. изучи текущую кодовую базу;
2. определи минимальные необходимые изменения;
3. реализуй;
4. запусти проект;
5. проверь ошибки;
6. исправь найденные ошибки;
7. только после этого переходи дальше.

Не переписывай работающую часть без необходимости.

Если существующий код прост и работает — сохраняй его.

# 36. Проверки

Добавить хотя бы базовые автоматизированные тесты для серверной игровой логики.

Особенно проверить:

```text
bot movement
resource collection
spawn cost
damage
attack range
death
winner detection
vision range
```

Не нужно строить огромную тестовую инфраструктуру.

# 38. Скрипты

Желательно:

```json
{
    "scripts": {
        "dev": "...",
        "start": "...",
        "test": "..."
    }
}
```

`npm run dev` должен запускать проект для локальной разработки максимально просто.

# 39. MVP считается готовым, когда

Можно выполнить следующую последовательность:

1. Запустить сервер.
2. Открыть сайт.
3. Создать комнату.
4. Открыть сайт во втором браузере.
5. Подключиться по коду комнаты.
6. Запустить матч.
7. Оба игрока получают базу и микробота.
8. На карте существуют ресурсы.
9. Игрок пишет программу.
10. Нажимает Apply.
11. Его боты начинают выполнять программу.
12. Боты ищут ресурсы.
13. Собирают их.
14. Создают новых ботов.
15. Обнаруживают противника.
16. Атакуют.
17. Уничтожают ботов и базы.
18. Один игрок остаётся последним.
19. Появляется экран победителя.
20. Хост может перезапустить матч.

Если эта последовательность работает — MVP завершён.

# 40. Главный приоритет

Если возникает выбор:

```text
красивая архитектура
или
рабочая игра
```

выбирать рабочую игру.

Если возникает выбор:

```text
универсальная система
или
простое решение для текущего ТЗ
```

выбирать простое решение.

Если появляется идея добавить функциональность, которой нет в ТЗ — не добавлять её.

Главная задача проекта:

**получить стабильную браузерную игру, в которой несколько учеников программируют поведение армий микроботов и сражаются друг с другом.**
