# Microbots: взаимодействующие программы

Это руководство описывает обновлённую модель программируемых агентов. Старые руководства про единый скрипт армии, встроенный AI, `nearestEnemy()` и мгновенный `collect()` относятся к предыдущей версии. Актуальная справка также доступна внутри игры.

## Что исполняет движок

Матч начинается с базы и одного бота с `programId = "default"`. Программы изначально пустые. Движок не выбирает цели, не добывает, не атакует и не создаёт ботов за игрока. Даже при наличии запасов производство начинается только после команды Base Controller.

Команда `moveTo()` задаёт движение на текущий тик. Для продолжения маршрута программа должна повторять её. Координаты маршрута можно хранить в `memory`. Пустой код и обработчик без действий оставляют бота на месте.

В редакторе можно создавать именованные программы, переключаться между их черновиками и отдельным Base Controller. У каждой программы есть конструкция: очки `speed`, `armor`, `attack`, `vision`, `cargo`, `communication`, `cpu`, `energy`. Суммарный бюджет задаёт `designPoints` в конфиге. Изменение конструкции относится к новым ботам; изменение кода применяется к ботам соответствующего `programId`. Имена программ не являются встроенными классами.

## Язык

Это ограниченный Python-подобный DSL, а не Python или JavaScript. Он поддерживает числа, строки, логические значения, `null`, списки и словари, `if/elif/else`, `for item in list`, `pass`, арифметику, сравнения, `and/or/not`, доступ `object.field` и `object["key"]`. Произвольные функции, импорт и доступ к среде сервера отсутствуют.

Код верхнего уровня исполняется каждый тик. Вместо него можно объявлять обработчики:

```python
def on_spawn():
    memory["ticks"] = 0

def on_tick():
    memory["ticks"] = (memory["ticks"] or 0) + 1

def on_message(message):
    memory["last_message"] = message.payload

def on_damage(attacker):
    memory["damaged"] = true
```

Обычные переменные временные. `memory` принадлежит конкретному боту, переживает тики и исчезает с ботом. Чтение отсутствующего ключа словаря возвращает `null`. Base Controller имеет собственную локальную память. Вложенность и объём сохраняемых данных ограничены; циклы и ключи прототипов запрещены.

## Наблюдение и действия

| API | Назначение |
| --- | --- |
| `scan()` | Публичные записи объектов в собственном радиусе обзора: `id`, `type`, `x`, `y`, `distance`, `ownerId` для принадлежащих игрокам объектов, `resourceType` для ресурсов. |
| `getPosition()`, `getHealth()` | Собственная позиция и здоровье. |
| `getBase()` | Координаты своей живой базы либо `null`. |
| `moveTo(x, y)` / `moveTo(target)` | Явное движение в текущем тике. |
| `attack(target)` | Попытка атаки видимой цели в пределах дальности и перезарядки. |
| `mine(target)` | Добыча конкретного близкого ресурса в груз. |
| `getCargo()` | Груз по типам `metal`, `energy`, `silicon`. |
| `unload(base)` | Разгрузка у своей базы. |
| `getEnergy()` | Текущая энергия агента. |
| `getTags()`, `setTag(key, value)` | Пользовательские метаданные без встроенной логики ролей и отрядов. |
| `distance(target)`, `random()`, `len(list)` | Простые операции над доступными данными. |

Цель выбирает сам код, обрабатывая `scan()`. Запомненные координаты не дают знания об актуальном положении скрытого объекта. Бот не получает глобальные запасы, список всей армии или сведения о необнаруженных противниках.

Ресурс `energy` на складе и энергия действий бота — разные величины. Добыча создаёт груз, разгрузка пополняет склад; энергия действий восстанавливается по правилам конфига. Характеристики конструкций влияют на стоимость производства. Баланс находится в `server/game/config.js`.

## Локальная связь

`send(channel, payload)` отправляет данные своим агентам в радиусе связи отправителя. Сообщение содержит `sender`, `channel`, `payload`, `tick` и доступно на следующем тике. База участвует в этой же локальной сети. Вражеские и удалённые агенты сообщение не получают. `receive()` позволяет прочитать входящие сообщения; альтернативный способ обработки — `on_message(message)`. Оба интерфейса могут видеть одни и те же сообщения: используйте один способ обработки либо предусмотрите дедупликацию. Повторный `receive()` в одном тике возвращает пустой список.

Например, ретранслятор существует только потому, что игрок написал пересылку:

```python
def on_message(message):
    if message.channel == "sighting":
        send("order", message.payload)
```

Другой агент может запомнить доставленную команду и продолжать исполнять её:

```python
def on_message(message):
    if message.channel == "order":
        memory["target"] = message.payload

def on_tick():
    if memory["target"]:
        moveTo(memory["target"])
```

Подтверждения доставки, дедупликация, выбор маршрута и защита от циклической пересылки остаются задачей программы игрока. Очереди и размер сообщений ограничены.

## Base Controller

Только контроллер базы может использовать `getResources()`, `getBots()`, `count(programId)`, `canSpawn(programId)` и `spawn(programId, tags)`. Он знает собственные запасы и ботов, собственные наблюдения и дошедшие до базы сообщения. Глобального обзора противника нет.

Сначала нужно зарегистрировать используемые программы, затем явно применить код базы:

```python
def on_tick():
    if count("miner") < 3:
        if canSpawn("miner"):
            spawn("miner", {"group": "supply"})
    elif count("scout") < 1:
        if canSpawn("scout"):
            spawn("scout")
```

База не принимает решения по умолчанию. Этот пример — обычный редактируемый пользовательский код.

## Ограничения и видимость

CPU учитывает выражения, условия, итерации и стоимость API. Все обработчики одного агента разделяют бюджет тика. При исчерпании остаток исполнения пропускается до следующего тика; уже подготовленные допустимые действия сохраняются. Энергия отдельно ограничивает физические действия, сканирование и связь. Увеличение CPU не создаёт дополнительную энергию.

Ошибка компиляции сохраняет предыдущую рабочую программу. Ошибка исполнения отменяет подготовленные действия и изменения памяти этого агента за тик. Остальные агенты продолжают работу. Интерпретатор не исполняет произвольный код среды сервера.

Клиент получает персональный серверный снимок. Видимость игрока — объединение обзоров его живых ботов и базы. Скрытые сущности и запасы противника не отправляются. `lastSeen` содержит только прошлое наблюдение с тиком обнаружения; оно не обновляется по скрытому состоянию. Если старая позиция снова наблюдается пустой, отметка удаляется. При перезапуске память, сообщения и история наблюдений сбрасываются; программы и конструкции сохраняются.

## Проверки

Серверные тесты используют встроенный `node:test`: `cd server && npm test`. Проверяются бездействие, изоляция программ и памяти, сенсоры, экономика, связь, бюджеты, производство, победа и приватность сетевых снимков.

Клиент: `cd frontend/client && npm run lint`, затем `npm run build`. Браузерный сценарий: `cd server && npm run test:browser`; по умолчанию используется установленный Edge. Для установленного Playwright Chromium задайте `BROWSER_CHANNEL=chromium`. Сценарий проверяет два клиента, программы и конструкции, производство базы, раздельный обзор и перезапуск; снимки экрана сохраняются в `artifacts/`.
